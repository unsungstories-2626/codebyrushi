Why this notebook exists

Most programming tutorials are written by people who already understand the subject, for readers who apparently already understand half of it too. Every explanation assumes vocabulary you don't have yet, so you end up looking up three other terms just to understand the definition of the first one.

I started learning to code the unusual way: by building real, working apps with an AI coding agent first, and reverse-engineering the underlying concepts afterward. That order — build, then understand — turned out to be a genuinely good way to learn, because every concept arrives already attached to a reason you needed it. This site is the running notebook from that process: short, plain-language write-ups of the ideas that actually made things click, published as I learn them.

If you're self-taught, coming from a non-technical background, or just tired of explanations that assume too much, this is written for you specifically. Read more about the approach on the about page.

How I actually learn this stuff

I don't sit down with a textbook. Most days start with a real feature I want to build, a prompt to an AI coding agent, and a lot of reading the code it hands back line by line until I understand why it's shaped that way. When something breaks, that's usually the moment I learn the most — chasing an error down forces you to actually understand the piece that failed, not just skim past it.

The habit that's made the biggest difference is refusing to move on until I can explain a concept back in my own words, without jargon. If I can't, I write the plain-language version down — and that note usually turns into one of the posts here. It's slower than copy-pasting a fix and moving on, but six months in, it's the difference between having built a lot of things and actually understanding how they work.

None of this requires a computer science degree or years of study before you're allowed to build something real. It requires curiosity about the "why" behind the code that already works, and a willingness to stay with a confusing error for five more minutes instead of giving up on it.
